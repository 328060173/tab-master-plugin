# 账号体系与功能分级

> Status: Draft · Author: plugs-pm · Date: 2026-07-12 · Feature slug: `account-and-membership`

---

## 1. 背景与目标

### 现状/痛点
- 插件目前纯本地功能,无账号体系,无法跨设备同步数据
- 设置菜单中「登录账号」「云同步」「快照」都是灰显占位
- 无运营变现渠道,长期发展受限
- 无用户反馈渠道,无法收集用户需求
- 用户不知道如何联系作者/加群交流

### 目标
本期实现:
1. **完整功能分级体系**——将所有现有功能+规划功能划分为「未登录可用」「已登录可用」「VIP会员可用」三级,未登录可用约71%
2. **设置菜单6项**——注册/登录/加群联系我们/意见反馈/操作说明/请作者喝咖啡
3. **登录引导位**——首页+稍后处理页顶部banner引导登录
4. **基础账号体系**——邮箱验证码登录,token管理,登录状态持久化

### 非目标(详见 §9)
- 不做第三方登录(Google/微信等)
- 不做付费会员功能落地(仅占位和文案)
- 不做云同步功能落地(仅分级和文案)
- 不做快照功能落地(仅分级和文案)

### 成功指标
- 设置菜单 6 项点击路径无 bug
- 登录链路零崩溃
- 登录状态保持7天以上
- 反馈功能可正常提交

## 2. 用户场景与故事

### 用户画像
- **普通用户**:未登录,使用基础功能(60%+),偶尔看到引导
- **活跃用户**:已登录,使用全部免费功能,愿意反馈问题
- **付费用户**:VIP会员,使用全部功能,支持作者发展
- **问题用户**:遇到问题,需要联系客服/加群/提反馈

### User Story
- **US-1**:作为未登录用户,我想在首页看到清晰的登录引导,以便了解登录能获得什么好处
- **US-2**:作为用户,我想用邮箱验证码登录,以便跨设备同步我的数据(本期仅注册,同步功能暂缓)
- **US-3**:作为用户,我想在设置里找到反馈入口,以便告诉作者我的问题和建议
- **US-4**:作为用户,我想加入用户群,以便和其他用户交流使用心得
- **US-5**:作为喜欢插件的用户,我想请作者喝杯咖啡,以便支持插件持续开发

### 关键路径
```
未登录用户打开插件
  → 首页顶部看到「登录获取更多功能」banner
  → 点击banner → 打开登录弹窗
  → 输入邮箱 → 获取验证码 → 输入验证码 → 登录成功
  → banner消失 → 解锁已登录功能
  → 去设置菜单 → 可以使用反馈功能
```

#### 4.A.2 分级方案:前端内置 vs 后端返回

**推荐方案:前端内置为主,后端兜底**

| 维度 | 前端内置 | 后端返回 | 推荐方案 |
|---|---|---|---|
| 更新便利性 | 需发版 | 可热更新 | 核心功能前端内置,新功能后端返回 |
| 版本碎片化 | 无,代码统一 | 老版本可能不认新功能ID | 功能ID永久不变,老版本忽略新功能 |
| 离线可用 | 完整可用 | 降级到前端内置 | 前端内置作为降级方案 |
| 灰度能力 | 无 | 可按用户/版本灰度 | 后端可灰度新功能 |
| 包体积 | 可忽略 | 0 | 前端内置影响极小 |
| 安全性 | 可被篡改 | 可信源 | VIP功能前端校验+后端二次校验 |

**具体实现**:
- 核心分级表内置在前端(`config/feature-tiers.ts`)
- 启动时请求后端 `GET /feature-tiers`（前缀待 api-backend 统一，见 §6.1）获取最新配置
- 后端返回的配置覆盖前端内置(增量更新,只返回变化项)
- 请求失败或无网络时,使用前端内置配置兜底

### 4.C 登录引导位

#### 4.C.1 首页Banner

```
┌─────────────────────────────────┐
│ [✕]  🔓 登录获取更多功能 →     │ ← Banner条
└─────────────────────────────────┘
  搜索框 [_________________]
  导航栏 [首页][稍后][分组][历史]

```

**设计细节**:
- **位置**:搜索框上方,顶部通栏
- **文案**:「🔓 登录获取更多功能 →」
- **关闭按钮**:左侧✕,可关闭
- **频控**:关闭后7天内不再显示
- **登录后**:永久消失
- **视觉**:浅灰背景,小号字体,不突兀
- **可感知**:
  - 事前:文案明确说明点击后会发生什么
  - 事中:点击后打开登录弹窗,有加载状态
  - 事后:登录成功banner消失,toast提示

#### 4.C.3 频控逻辑

```typescript
// 关闭Banner后,记录时间戳
chrome.storage.local.set({
  loginBannerDismissedAt: Date.now()
})

// 下次打开时检查
const { loginBannerDismissedAt } = await chrome.storage.local.get(['loginBannerDismissedAt'])
const sevenDays = 7 * 24 * 60 * 60 * 1000
if (loginBannerDismissedAt && Date.now() - loginBannerDismissedAt < sevenDays) {
  // 7天内,不显示
} else {
  // 超过7天,重新显示
}
```

### 4.D 边界状态

| 场景 | 系统行为 |

## 6. 接口契约

### 6.1 基础约定

- **Base URL**: 待定(正式环境/测试环境)
- **请求头**:
  - `Content-Type`: `application/json`
  - `X-App-Platform`: `chrome-extension` (常量)
  - `X-App-Version`: `{版本号}` (读manifest)
  - `X-App-Code`: `tabmaster` (常量)
  - `Authorization`: `Bearer {token}` (已登录时)
- **路径前缀待 api-backend 统一**：沿用现有 Controller 风格还是加 /api 前缀，由 api-backend 定
- **响应格式**：由 api-backend 按若依 `R<T>` 规范实现 (`{code, msg, data}`)

### 6.2 接口列表

| 接口 | 方法 | 路径 | 说明 | 授权 |
|---|---|---|---|---|
| 获取功能分级表 | GET | `/api/feature-tiers` | 获取最新功能分级配置 | 否 |
| 发送登录验证码 | POST | `/api/email/send-login-code` | 给邮箱发送验证码 | 否 |
| 邮箱验证码登录 | POST | `/api/login/login-by-email-code` | 使用邮箱+验证码登录 | 否 |
| 刷新Token | POST | `/api/login/refresh-token` | 使用refreshToken刷新token | 否 |
| 提交反馈 | POST | `/api/feedback/suggest` | 提交用户反馈 | 是 |
| 获取用户信息 | GET | `/api/user/me` | 获取当前用户信息 | 是 |
| 获取VIP开通链接 | GET | `/api/vip/purchase-url` | 获取VIP会员购买页面链接 | 是 |

## 7. 性能 / 安全 / 兼容

### 7.1 性能预算

- Banner显示: ≤ 20ms
- 登录弹窗打开: ≤ 50ms
- 登录请求超时: 10s
- 反馈提交超时: 10s
- 存储读写: ≤ 30ms

### 7.2 安全

- Token存储在`chrome.storage.local`,不存储在`localStorage`
- HTTPS强制,不允许HTTP请求
- XSS防护:用户输入(反馈内容)不使用`v-html`,转义后显示
- CSRF防护:请求头带token,验证来源
- 敏感信息(邮箱)不在日志中输出完整内容(脱敏:u***@example.com)
- 退出登录时清除所有auth数据

### 7.3 兼容

- **目标矩阵**: Chrome 102+ / Edge 102+ × macOS / Windows
- **API检测**: `chrome.storage.local` 稳定API,无需检测
- **降级**:
  - 网络请求失败 → 使用前端内置功能分级表
  - 提交反馈失败 → 保存到离线队列,网络恢复后重试
- **系统弹窗**: 复制功能使用`navigator.clipboard.writeText`,降级到`document.execCommand('copy')`
